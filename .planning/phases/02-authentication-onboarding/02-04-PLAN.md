# Plan 02-04: SignatureModal Component + Execute-Signature Edge Function

## Objective

Build the reusable `<SignatureModal>` component used for all 7 signature types on the platform (consulting agreement, grant writing auth, grant submission auth, lender intro auth, success fee acknowledgment, monthly report auth, CROA agreement). Implements the full 6-step signature flow from the build spec: document display with scroll enforcement, identity verification, signature capture in Dancing Script font, client-side audit data capture, server processing via `execute-signature` edge function, and PDF generation with triple-redundant storage.

## Context

- Working directory: `C:\projects\cosby-capital`
- Build spec Section 9 (AGREEMENTS & SIGNATURES) — 7 signature types
- Build spec Section 10 (DOCUMENT MANAGEMENT) — triple-redundant storage
- Signature flow from spec: display → identity verify → signature capture → audit capture → server process → PDF + storage + email
- Legal basis: E-SIGN Act (15 U.S.C. § 7001) and Alabama UETA
- Fonts: Dancing Script for signature rendering (add to Google Fonts import in layout.tsx)
- Triple storage: Supabase Storage bucket `client-documents`, AWS S3, Google Drive service account
- Security: server-side timestamp only (never client-supplied), homograph attack normalization (Unicode NFC)
- Phase 1 utilities: lib/logger.ts, lib/sanitize.ts, lib/auth.ts, lib/supabase.ts

## Tasks

### Task 1: Create signature tables migration
Create `supabase/migrations/20240101000008_signature_tables.sql`:

```sql
CREATE TABLE signatures (
  id uuid primary key default uuid_generate_v4(),
  created_at timestamptz default now(),
  client_id uuid references clients(id) not null,
  document_type text not null check (document_type in (
    'consulting_agreement', 'grant_writing_auth', 'grant_submission_auth',
    'lender_intro_auth', 'success_fee_acknowledgment', 'monthly_report_auth',
    'croa_agreement'
  )),
  document_version text not null default 'v1.0',
  -- Signed by info
  signed_by_name text not null,
  signed_by_email text not null,
  signed_at timestamptz not null, -- set server-side only
  -- Audit trail
  signed_ip text,
  signed_user_agent text,
  device_fingerprint_hash text,
  document_hash text not null, -- SHA-256 of document text
  audit_hash text not null, -- SHA-256 of (document_hash + signed_by_name + signed_at + signed_ip)
  document_text_snapshot text not null, -- full document text at time of signing
  -- Storage confirmation
  supabase_path text,
  s3_path text,
  google_drive_file_id text,
  storage_verified boolean default false,
  -- Email delivery
  client_email_sent boolean default false,
  admin_email_sent boolean default false
);
ALTER TABLE signatures ENABLE ROW LEVEL SECURITY;
CREATE POLICY "sig_own_read" ON signatures FOR SELECT
  USING (client_id IN (SELECT id FROM clients WHERE user_id = auth.uid()));
CREATE POLICY "sig_service_write" ON signatures FOR INSERT
  WITH CHECK (auth.role() = 'service_role');
-- Immutable: prevent tampering
CREATE RULE no_update_signatures AS ON UPDATE TO signatures DO INSTEAD NOTHING;
CREATE RULE no_delete_signatures AS ON DELETE TO signatures DO INSTEAD NOTHING;
```

### Task 6: Create execute-signature API route
Create `src/app/api/signature/execute/route.ts` (POST):
- Auth required, verifyOwnership check
- Input (Zod):
  ```typescript
  {
    document_type: string,
    signed_name: string (max 200),
    document_hash: string (64 chars),
    device_fingerprint_hash: string (max 64),
    user_agent: string (max 500)
  }
  ```
- Server-side:
  1. Get client record, verify `signed_name` matches `clients.owner_name` (Unicode NFC normalized on both)
  2. Set `signed_at = new Date().toISOString()` — NEVER use client-supplied timestamp
  3. Get client IP from `x-forwarded-for` header
  4. Compute `audit_hash = SHA-256(document_hash + signed_name + signed_at + client_ip)`
  5. Call `execute-signature` Supabase edge function with all audit data
  6. Edge function handles: DB insert, PDF generation, storage, emails
  7. Return `{ signature_id: string }`
- Minimum response time: 50ms (consistent timing, S16-004)

### Task 7: Create execute-signature Supabase edge function
Create `supabase/functions/execute-signature/index.ts`:
- Called by the API route (internal, INTERNAL_SERVICE_SECRET header required)
- Input: all signature audit fields + client_id
- Steps:
  1. Insert to `signatures` table with all fields (server-set `signed_at` — not from client)
  2. Call `generate-pdf` edge function to create executed PDF
  3. Upload PDF to Supabase Storage (`client-documents` bucket, private)
  4. Upload PDF to AWS S3 (AES-256, path: `/clients/[client_id]/[YYYY-MM]/[DD]_[doc_type]_v1.0_executed.pdf`)
  5. Upload PDF to Google Drive (service account, parent folder for client)
  6. Re-fetch all 3 and compute SHA-256 — verify all 3 match → set `storage_verified=true`
  7. Send email to client via Resend (PDF as attachment): "Your executed consulting agreement is attached"
  8. Send email to info@cosbycapital.com: "New client agreement executed: [business_name]"
  9. Update `client_email_sent=true, admin_email_sent=true`
  10. Return `{ signature_id, storage_verified: true }`
- If any storage upload fails: retry once, then log + Telegram alert + return partial success
